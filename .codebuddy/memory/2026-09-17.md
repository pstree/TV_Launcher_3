## 首页右上角「设置」改为悬浮面板（不再遮盖全屏）

用户要求：点击顶部栏右侧设置按钮后弹出的面板改为悬浮窗，不要遮盖全部屏幕。

### 改动
- `components/dialog/SettingsDialog.kt`：
  - 删除整屏 `Color.Black.copy(alpha = 0.7f)` 遮罩；Dialog 内容根节点保留 `Box(fillMaxSize)` 但**全透明**，改为承载"点击空白处关闭"的背板（`detectTapGestures { onDismissRequest() }`）。
  - 面板本体 = `Column`（`RoundedCornerShape(16.dp)` + `OnWallpaperContainer`，与主屏图标网格容器一致）贴在 `Alignment.TopEnd`，上边距 `PADDING_DIALOG_EDGE + topBarHeight.dp`、右/下各 `PADDING_DIALOG_EDGE` → 卡片挂在顶部栏下方，时钟与 tab 行仍然可见。
  - 网格 `LazyVerticalGrid` 由 `fillMaxHeight()` 改为随内容自适应（LazyList/LazyGrid 主轴默认 wrap content，高度 = `constraints.constrainHeight(内容高度)`），面板高度 ≈ 420dp（5 行 × 60dp + 间距 + 20dp padding）。
  - 面板 `Column` 上加 `pointerInput { detectTapGestures(onTap = {}) }`，吃掉落在面板自身/按钮间隙的点击，避免误触背板关闭。
  - `DialogProperties.dismissOnClickOutside = false`：Compose 平台的"点外部关闭"是按**内容子 View 矩形**（`DialogLayout.isInsideContent`）判定的，内容铺满全屏时永远判定为"内部"而失效，所以必须自建背板。
  - 移除了面板内的 时间/日期 头部（`TimeText` + `DateAndWeekdayText`）：原来有它是因为黑遮罩把顶部栏时钟挡住了；现在面板挂在顶部栏下方、时钟仍可见，头部就是重复信息，去掉后卡片也更紧凑。
- `ui/launcher/activity/MainActivity.kt`：`SettingsDialog` 不再需要 `timeViewModel`，相应删掉 `TimeViewModel` 字段与 import。
  - 副作用：`components/text/TimeText.kt` 与 `ui/launcher/viewmodel/TimeViewModel.kt` 目前**无调用者**（保留未删，属可复用组件；若之后要恢复时钟或做桌面时钟可直接用）。

用户要求：点首页 tab「文件」后，下面的文件列表加半透明背景。

- 原因：列表本来就有 `OnWallpaperContainer`（LightGray 30%），但壁纸换成必应每日壁纸这类浅色图后 30% 浅灰几乎不可见，看着像没有背景。

- 设置悬浮面板（`SettingsDialog`）：用户随后确认"对，换成深色面板"，已一并换成 `OnWallpaperContainerDark`。
- 仍用浅色 `OnWallpaperContainer` 的地方（**未改**）：`MainActivity` 顶部栏 TabRow/时钟、`IconButtonTv`（顶部栏设置按钮）、`HomeScreen` 主屏固定图标网格、`AppsScreen` 应用列表。

## 设备连接（adb）现状
- 本机 adb 用的是 **qadb 自带二进制**：`/home/qian/.qadb/adb-cache/adb/linux/adb`（版本 37.0.0-14910828，1.0.41）。用户机器上还装了 `qadb-2.1.2-1-x86_64.pkg.tar.zst`（GUI 工具），server 进程形如 `adb -L tcp:5037 fork-server server --reply-fd 4`。
- 2026-09-17 尝试连接：`adb devices` 为空；`lsusb` 只有鼠标/无线接收器/蓝牙适配器，**没有任何 Android 设备** → USB 线没插好或没开 USB 调试；`adb mdns services` 无发现；`adb connect 192.168.3.117:5555` 仍 `Connection refused`（电视侧"网络调试"未开）。ping 电视 192.168.3.117 正常（~150ms）。
- 用户二次自查"USB 连上了"后复检：`lsusb` 与内核 `ls /sys/bus/usb/devices/*/idVendor`（1-5 鼠标 / 1-6 无线接收器 / 1-11 蓝牙 / usb1,usb2 root hub，无新增）→ **内核层根本没有任何新 USB 设备**，问题不在 adb 而在物理连接/设备形态。`dmesg` 无权限（Operation not permitted），只能用 sysfs 判定。
- 结论/建议：Android TV **一体机**的 USB 口基本都是 host 口（插 U 盘/键鼠），不能反向作为 USB 设备连电脑做 adb；只有带 OTG/调试口的盒子才行。这台电视 192.168.3.117 网络可达，最实际的是在开发者选项里开"网络调试/ADB over network"后 `adb connect 192.168.3.117:5555`。

## 冷启动性能修复（用户反馈"第一次打开桌面非常慢"）

先做了双轴并行审计（用 code-review skill 的结构，轴改为「冷启动关键路径」/「首帧渲染+构建配置」），根因是**启动时无条件干了与 Home 首屏无关的全量活**：
枚举全部可启动应用（N×(2~3 次 PackageManager IPC + 图标光栅化 + Palette 调色板量化，`LauncherViewModel.init` 触发）＋ 每次 `ON_RESUME` 重建全屏壁纸位图 ＋ 启动预热 Files 卷列表；叠加 debug 包（无 R8）与首次安装无 ART profile。

### 改动（8 个文件，编译 + lint 通过）
1. `LauncherViewModel`：`init` 不再跑 `updateActivityModelList(INIT)`；新增 `ensureActivityModelListLoaded()`（`@Volatile activityModelListLoadRequested` 单次守卫），由 `AppsScreen` / `AppListDialog` 的 `LaunchedEffect` 调用；`onConfigChanged` 的 locale 重建也加了同一守卫。
2. `ActivityModel`：删掉 `color` 字段（连带 `@ColorInt`/`DrawableUtils` 依赖），`fromResolveInfo` 只做 1 次 label + 1 次 `ApplicationUtils.getIconType()`（与旧 `getActivityIconPair` 的 banner 判定同义，但不再加载图标 drawable）。
3. `ActivityButtonTv`：底色改为 `produceState(initialValue = ButtonContainerDefault/Transparent, key1 = model.getKey())` + `withContext(Dispatchers.IO)` 按**可见项**现算 → 成本从 N 降到 ~可见的 10~20 项。
4. `ApplicationUtils.getIconType()`：新增，等价于 `getActivityIconPair` 的 `banner != null → Banner`，省掉 `getActivityIcon` 那次 IPC。
5. `DrawableUtils`：`toBitmap` 的 1×1 退化改为 `FALLBACK_RASTER_SIZE = 192`（`AdaptiveIconDrawable.intrinsicWidth` 常为 -1，原先量化的是 1 个像素 → 底色随机）。
6. `MainActivity`：壁纸抽成 `loadWallpaperSnapshot(previousId)` + `decodeWallpaper(wm)`，用 `getWallpaperId(FLAG_SYSTEM)` 去重 —— 首启原先会被 `LaunchedEffect(Unit)` 与 `LifecycleObserver`（`addObserver` 会向新观察者补发 ON_RESUME）各跑一遍，现在同 id 直接复用；顺手把 `Bitmap.createBitmap` 换成 KTX `createBitmap` 消掉 UseKtx 告警；移除 `filesViewModel.onConfigChanged()` 的启动预热（Files tab 首次可见时 `FilesScreen` 自己 refresh）。
7. 有意**未改**：`registerPackageBR()` 仍留在 `init` 同步执行 —— 它是单次 binder (~1ms)，挪到 IO 协程会引入 `onCleared` 与注册完成的竞态（可能泄漏 receiver），收益/风险不划算。
